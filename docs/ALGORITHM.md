# 算法说明（`adaptive-v2`）

本文说明作息调整算法 `adaptive-v2` 的规则、常量与工程取舍。目标作息与历史依据、步长曲线、
前移/后移不对称、三餐锚点、偏离三档、计划快照与达标率口径都在这里；每条规则的文献出处指向
[REFERENCES.md](REFERENCES.md) 的条目编号。接口字段与请求方式见 [API.md](API.md)。

> 一句话概括：**用“每天一小步、前移比后移更保守”的方式把作息推到目标点，三餐只作为可执行的
> 节律锚点而非相位杠杆，用户偏离计划时按偏离幅度分档处理，所有建议都以快照形式留痕。**

## 1. 目标作息与历史依据

- **目标来源有两种**：用户自定义目标（`/api/settings/target` 设置 `target_sleep_time` /
  `target_wake_time`，两个时间必须同时设置或同时清空），或系统按历史记录推断的默认目标。
  响应里的 `source` 字段会标注 `custom_target` 或 `system`。
- **系统目标是“统计规律”不是“个体处方”**：先取最近一段时间的入睡/起床中位数作为基准线
  （`basis` 字段给出参与统计的样本天数与派生值），再向更健康的方向收敛。样本不足时会缩短
  计划天数并给出 `advice.notice.*` 提示（例如计划被截短需要用户确认的那条）。
- **依据**：群体统计显示成人睡眠时长与就寝时间的规律，以及相位前移训练的有效速率区间
  —— 见 [REFERENCES.md](REFERENCES.md) 的 Eastman 2005（相位前移速率）、以及睡眠时长/就寝时间的
  人群统计条目。**前移速率有文献支撑，具体到“用户该几点睡”是工程推断值。**

## 2. 天数与步长曲线（形状函数）

计划按“把基准线推到目标点需要多少天”计算（`days` 可被请求参数覆盖，范围 1–30；用户选几天就是几天）。
曲线**不是固定分段表**，而是由**总偏移 `D` 与天数 `N`** 现场生成的一条连续函数：

```
φ(u) = 1 + α·(1 − u)^p        u = (i − 1) / (N − 1)，i = 1…N
s_i  = D · φ(u) / Σφ          再按“累计取整”分配成整数分钟，且 Σs_i = D
```

- 参数 `STEP_SHAPE_ALPHA = 0.6`、`STEP_SHAPE_POWER = 1.0`，都在 `backend/app/services/advice.py`。
- **先快后缓**：曲线从第一天的高点单调衰减到最后一天的低点，但**永远衰减不到 0**。
- **收尾速度只由 α / p 决定，与天数无关**：`s_N / s_1 = 1 / (1 + α) ≈ 0.62`，
  `s_1 / 日均 = (1 + α) / (1 + α/2) ≈ 1.22`。也就是说无论计划排 3 天还是 30 天，
  第一天总是日均的 1.22 倍、最后一天仍保留第一天约 62% 的速度。
- **为什么不再用固定分段**：旧版把“每天上限”写成 60/45/30/15，天数一多就走到 15 分钟/天、末尾几乎不动，
  而“最后一天必须落在目标上”又会把差额整块压到末日（300 分钟 / 7 天 → 45,45,45,45,30,30,**60**，
  末日反而最大）。形状函数没有“走到头”的问题：每天都按同一条曲线分配，末日自然还在移动。
- **单调性与落地**：曲线严格单调不增；累计移动量在计划最后一天**正好落在目标点**（不许留在半路，
  也不许超过）。单元测试 `tests/test_advice_engine.py::test_step_curve_is_decreasing_and_lands_on_target`、
  `::test_step_profile_is_smooth_and_keeps_speed_at_the_end`。
- 请求参数 `mode` 只有 `fast` / `slow`：`fast` 固定 1 天（整天就是一次移动），`slow` 用请求的天数；
  两者只改变步子分配，不改变目标点。
- **“每天不超过 60 分钟”只是提示**：`STEP_CAP_ADVANCE = STEP_CAP_DELAY = 60` 不再截断曲线，
  只用于判断 `feasible` 与生成提示文案（见第 3 节）。
- 返回体 `steps` 报形状参数与三天的实际步长：`shape {alpha, power}`、`first_step_minutes`、
  `max_step_minutes`、`last_step_minutes`；每天具体多少分钟看 `plan[*].step_minutes`。
- **天数不够时**：`feasible = max(s_i) <= 60`。不满足时计划照旧按曲线排满 `N` 天（末日仍落在目标上），
  只是第一天（最大一步）超过 60 分钟 —— 提示把代价写清楚：`advice.steps.infeasible` /
  `advice.notice.infeasible` 的 `{step}` 就是这个最大步长、`{cap}` 是 60。单元测试
  `::test_last_step_minutes_reports_the_final_day`、`::test_infeasible_notice_names_the_biggest_step`
  守着“提示里的数字 == 日卡上的数字”。
- **界面上的“步长曲线”**：把 `plan[*].step_minutes` 逐日累加成一条曲线（横轴天数、纵轴“到那天为止
  一共移动了多少分钟”），用单调三次插值（Fritsch–Carlson）画成平滑曲线，并用一条“平均速度”虚线
  （原点 → 终点）做对照：曲线在虚线上方说明前几天走得比平均快，这正是“先快后缓”的视觉表达。
  某天步长超过每日提示阈值时，该点变暖色。数据只来自日卡已有字段，所以加固前的老方案快照也能画；
  实现见 `frontend/user/js/pages/advice.js` 的 `cumulativeSteps()` / `smoothPath()` / `curveCardHtml()`。
- **图上另外三条信息**：① 一条点线从原点按“每天顶到 60 分钟”的斜率往上（裁在绘图区内），它与顶边
  （= 目标）相交的那一格就是“按上限速度第几天能到”——落在计划天数之外时只画线不画标记；② 点某天会
  弹出气泡（当天步长 / 已移动 / 是否超阈值），并高亮、滚动到对应日卡（气泡数字与日卡数字同源）；
  ③ 天数滑块一拖，曲线当场按新天数重画并标“预览”——用的是同一套形状函数（`shapeSteps()` 是
  `_shape_steps()` 的 JS 版，含“累计取整 + 单调借平”），只是不写库；卡片上的
  `data-curve-selfcheck` 每次渲染都会拿现算结果与日卡逐项比对（允许 ±1 取整差），对不上就是有人只改了
  一边的公式，探针会直接报 `mismatch`。

## 3. 每日阈值：前移与后移共用 60 分钟

- 文献事实：相位**前移**受内在昼夜节律周期（略长于 24 小时）抵抗，前移过快会出现入睡困难与睡眠效率下降；
  **后移**顺应节律，代价小得多。Eastman 2005 的对照实验里 1 小时/天约等于实际 30 分钟/天的有效前移，
  2 小时/天约 36 分钟/天并已出现睡眠效率下降；跨时区飞行估计西行（后移）约 92 分钟/天、
  东行（前移）约 57 分钟/天 —— 见 [REFERENCES.md](REFERENCES.md) 的 Eastman 2005 条目。
- 工程取值：`STEP_CAP_ADVANCE = STEP_CAP_DELAY = 60` 分钟/天。取 60 而不是文献里的 30/36，是因为
  “1 小时最适宜、2 小时也没问题”是产品侧的初始要求（`STEP_CAP_HARD = 120` 也来自那里）；
  而两边取同一个数，是因为旧版“后移 90 > 前移 45”的不对称并没有文献直接把“45/90”写出来
  （92 vs 57 是跨时区飞行估计，不是治疗建议）。
- 这两个常量现在只做**提示阈值**，不截断曲线（见第 2 节）。
- 单元测试 `::test_both_directions_share_the_same_threshold` 守着“两边一致”这件事。

## 4. 三餐锚点窗口

三餐不是相位杠杆（2025 年综述没有任何“进餐移动昼夜相位”的证据），但固定时间的进餐是**可执行
的节律锚点**，所以算法给出建议窗口，并且用户可以逐餐开关
（`meal_breakfast` / `meal_lunch` / `meal_dinner`）：

| 餐次 | 窗口（相对锚点） | 锚点 | 说明 |
| --- | --- | --- | --- |
| 早餐 | 起床后 **15–30** 分钟 | 起床 | 窗口起点即 `best_time` |
| 午餐 | 窗口长 **120** 分钟，起点取早餐与晚餐的**中点**再提前 60 分钟 | 两端（`both`） | 再夹进 [起床+120, 晚餐−240] 分钟；受“连续未吃早餐”规则前移（见下节） |
| 晚餐 | 窗口长 **90** 分钟，起点为睡前 **270** 分钟（4.5 小时） | 入睡 | 与睡眠锚点挂钩，不跟起床时间一起平移 |

- **午餐为什么取中点**：早先午餐锚在“起床 + 180 分钟”，白天越长，午餐与晚餐之间就拉得越开
  —— 06:00 起、01:00 睡（白天 19 小时）的人午餐 09:00、晚餐 21:30，间隔 **12.5 小时**；
  改成取早餐与晚餐的中点后，同一作息的间隔收敛到 7.6 小时左右。
- **整体提前 1 小时**：中点与睡眠锚点算完后，午餐与晚餐一起前移 `MEAL_ADVANCE_MIN = 60` 分钟，
  让饭点整体靠前（晚餐从“睡前 3.5 小时”变成“睡前 4.5 小时”），吃完还留有活动时间。
- **现实作息窗口（就近靠拢）**：作息正常时，饭点不该继续跟着极端时刻线性漂移，而要贴回社会时钟：

  | 条件 | 约束 | 常量 |
  | --- | --- | --- |
  | 起床 ≤ **15:00** | 午餐就近靠拢进 **11:00–15:00** | `NORMAL_WAKE_UNTIL` / `LUNCH_NORMAL_WINDOW` |
  | 入睡不晚于次日 **06:00**（或当天 17:00 之后，都算夜里睡） | 晚餐就近靠拢进 **17:00–22:00** | `NORMAL_SLEEP_UNTIL` / `DINNER_NORMAL_WINDOW` |

  “就近靠拢”= **落在窗口外才夹回最近的边界，窗口内的取值原样保留**，因此不会把本来合理的
  饭点挪走；作息一旦越界（15:00 之后起床、或 06:00–17:00 之间补觉），这一步整体跳过，
  直接沿用上一步的相对锚点结果 —— 极端作息本来就不该硬套社会时钟。
  实测（改进后）：07:00 起 / 23:00 睡 → 早餐 07:15、午餐 **11:52**、晚餐 **18:30**；
  06:00 起 / 01:00 睡 → 06:15 / **12:22** / **20:30**；09:00 起 / 02:00 睡 → 09:15 / **14:22** / **21:30**。
- **保序优先于窗口**：午餐必须在早餐之后、晚餐之前，晚餐还要留在睡前 2 小时之外。窗口与极端作息
  打架时（例如 14:50 起床却要求 11:00 吃午饭）以顺序为准，这一条写在 `_meal_times()` 的第 ③ 步。
- 响应里每餐是 `MealPlan`：`enabled`、`best_time`（等于窗口起点，兼容字段 `time`）、
  `window_start`、`window_end`、`anchor`（`wake` / `sleep` / `both`）、`shifted_minutes`（因未吃早餐
  前移的分钟数）、`bar_minutes`（时间图上的条长，仅视觉）、`note`（i18n 键）。
- **三餐挂在“起床日”那一天**：一条记录跨两个日历日（`record_date` 入睡日、`wake_date` 起床日），
  `wake_day_of(record)` 是三餐、计划日卡片、打卡回写与达标率的配对键（老记录没有 `wake_date`
  时按“起床时刻 <= 入睡时刻 → 次日”推导，行为与老版本一致）；入睡日仍是睡眠统计、时间轴
  与保留策略的标签。所以“今天早餐吃了吗”看的是**今天早上醒来那一条记录**，
  见 `::test_meals_belong_to_the_wake_day`。
- **“起床后 X 分钟进食”这类钟点窗口在文献里并不存在**，它们是工程默认值；文献只支持
  “三餐作为节律锚点、不做相位移动”这一条，见 [REFERENCES.md](REFERENCES.md) 的 2025 年综述条目。

## 5. 午餐前移规则与连续未吃早餐计数

- 用 `POST /api/advice/checkin`（`meal` + `eaten`，可选 `date` 与 `refused`）记录“这一餐吃了没有”；
  记录会写回当天的睡眠记录。每餐的状态因此有四种：`eaten` / `skipped` / `refused` / `unknown`。
- **连续未吃早餐的天数**（`streak`）达到阈值后，午餐建议开始前移：前移量按 streak 递增
  （60 / 90 / 120 分钟），结果体现在 `MealPlan.shifted_minutes` 上。下限有两个：“不早于起床后
  2 小时”与社会时钟窗口的起点 **11:00**（作息正常时），所以前移在窗口里能走多少走多少。
- **“不想吃早餐”**（`meal="breakfast"` + `eaten=false` + `refused=true`）：与“跳过”一样计入
  连续未吃早餐，并且**当天的午餐与晚餐一起提前 60 分钟**（`REFUSED_BREAKFAST_SHIFT`）——
  晚餐提前 60，午餐再因为“取中点”跟着往前 30，所以阶梯从零起步时实测午餐共提前 **90** 分钟；
  若午餐已贴到窗口起点（11:00）或起床后 2 小时的下限，则实际位移相应变小。规则只作用于
  计划第一行（今天），明天起的建议不变。
- “不想吃”不重写已保存的计划快照，而是在读取时叠加（`apply_refused_breakfast_overlay()`）：
  否则 `plan_meta.replans`（“已重算 N 次”）会被打卡动作悄悄推高，历史计划也会被改写。
  点“已吃”即撤销（同一行 `refused` 写回 `false`）。
- **“点了会发生什么”先算出来**：`refusal_preview(payload, today, streak, missed_today)` 在生成/读取
  计划时就把“现在点不想吃”的结果算一遍（内部在深拷贝上叠加，再跑一次 `day_for`），随今日卡片
  以 `today.refusal_preview` 下发。它按**点完之后**的阶梯算（`streak if missed_today else streak + 1`）——
  这一点被 `::test_refusal_preview_matches_the_real_checkin` 抓过一次：早先用点击前的阶梯，
  窗口有空间时预测会比真实落库的时间差一格。所以界面上点击后立刻显示的数字，与请求回来的
  数字必须逐字段相同（`best_time` / `window_start` / `window_end`）。
- **文案约束**：带参数的句子（`{streak}` / `{shift}`）一律由前端用数字字段拼（`tp()`），后端
  只返回不带参数的文案键 —— 否则页面上会原样显示 `{streak}`。
- 测试：`::test_lunch_shifts_earlier_when_breakfast_skipped`、
  `::test_lunch_midpoint_keeps_gaps_reasonable_on_long_days`、
  `::test_checkin_eaten_true_writes_back`、`::test_refused_breakfast_pulls_today_meals_earlier`、
  `::test_refusal_preview_matches_the_real_checkin`。

## 6. 偏离三档

“当前计划”是一份快照；用户实际作息与快照对比得到偏离分钟数（取绝对值），分三档处理：

| 偏离幅度 | 处理方式 | 理由 |
| --- | --- | --- |
| **≤ 30 分钟** | 静默接受，不提示、不重算 | 属于正常波动，提示只会造成噪声 |
| **30–90 分钟** | 静默重算：自动把后续计划顺延/前移 | 已经偏离但仍属“同一天”，直接修正计划更省事 |
| **> 90 分钟** | 弹窗让用户选策略（`postpone` / `recompute` / `keep`） | 偏离足够大，必须由用户决定是顺延、重算还是保持原计划 |

- 静默重算**每天最多一次**（防止用户来回改动导致计划被反复重排），见
  `::test_auto_recompute_only_once_per_day`。
- 分档判定见 `::test_deviation_levels`；用户选择后走 `POST /api/advice/replan`，
  `strategy` 三选一，返回新的计划与 `plan_meta`。

## 7. 计划快照与重算

- 生成建议时默认 `save: true`，把当天的计划落库成**快照**（`plan_id` / `plan_meta.saved`），
  之后的偏离判定、达标率统计都以快照为基准，而不是每次重新计算。
- `GET /api/advice/plan` 取当前快照；`POST /api/advice/replan` 触发重算并写新快照；
  `plan_meta` 记录 `start_date`、`target_date`、`postponed_days`、`replans`、`saved`。
- 重算不会“抹掉历史”：快照是追加的，因此“当时建议了什么、后来改了什么”可追溯。
- 测试：`::test_plan_snapshot_deviation_and_replan`。

## 8. 达标率与连续天数口径

- **达标** = 当天实际入睡/起床落在快照给出的容差内（容差与偏离分档同源）。
- **按起床日配对**：计算达标率时，把每条记录按 `wake_day_of(record)`（起床日历日）对齐到计划里
  那一天 —— 夜里 23:40 睡、次日 07:20 起，算的是**次日**那天的达成情况；
  见 `::test_checkin_writes_back_to_the_wake_day_record`。
- **未记录不计入**：没有记录的那天既不记为达标，也不记为不达标，分母里直接排除
  —— 见 `::test_adherence_ignores_unrecorded_days`。
- **不中断**：连续达标天数（streak）只被“明确的不达标”打断，缺记录的日子不打断连续。
  这样偶尔忘记记录不会让用户看到“连续清零”。
- 统计结果用于建议页的达标率展示，字段随建议响应一起返回。

## 9. 24 小时时间图的数据结构与跨零点处理

- **轴窗不是 00:00–24:00**，而是「起床前 2 小时 → 入睡后 2 小时」（`_timeline()`，
  `backend/app/services/advice.py`）：`axis_start = wake − 120`、`axis_end = sleep + 120`。
  这样轴覆盖的是「醒着的一天 + 两头各 2 小时」，因此天然跨零点：入睡 01:30 / 起床 08:30 时
  `axis_start = "06:30"`、`axis_end = "03:30"`、`span_minutes = 1260`。
- 数据结构（`timeline` 字段，实测样例）：

  ```json
  {
    "axis_start": "05:05",
    "axis_end": "01:45",
    "span_minutes": 1240,
    "sleep_label": "23:45–07:05",
    "sleep_minutes": 1000,
    "items": [
      {"kind": "sleep", "segment": "morning", "start": 0, "end": 120,
       "start_time": "05:05", "end_time": "07:05", "partial": true},
      {"kind": "meal", "meal": "breakfast", "start": 135, "end": 165,
       "start_time": "07:20", "end_time": "07:35", "partial": false, "shifted_minutes": 0},
      {"kind": "sleep", "segment": "night", "start": 1120, "end": 1240,
       "start_time": "23:45", "end_time": "01:45", "partial": true}
    ]
  }
  ```

- 条目里的 `start` / `end` 是**相对轴起点的分钟偏移**（不是钟点字符串），前端直接按
  `start / span_minutes` 算百分比画条，不需要任何时间换算；`start_time` / `end_time` 是给人看的
  钟点，`sleep_label` 给出睡眠的完整区间（`入睡–起床`）。
- **跨零点处理**：整夜睡眠被轴窗切在两头 —— 贴入睡的那截落在轴尾（`segment: "night"`）、
  贴起床的那截落在轴头（`segment: "morning"`），两截都带 `partial: true`，中间那几个小时
  不在轴上（那时用户是醒着的，不需要画）。前端把两截分别标成「睡眠前段 / 睡眠后段」，
  并在轴上的睡眠徽标里补一句「跨零点，轴两端相接」，否则用户会以为"睡了两觉"。
- `sleep_minutes` 是未环绕前的 `sleep − wake`（排查用，前端不读它）。
- 每个 `DayPlan` 也有自己的 `timeline`（每日方案里的迷你时间图），结构与顶层一致；
  顶层 `timeline` 就是今日卡片那张的副本。
- 测试：`::test_timeline_wraps_around_midnight`（断言 `axis_start == "06:30"`、两截的
  `segment` / `partial` 与各自的 `start_time` / `end_time`）。前端绘制逻辑在
  `frontend/shared/timeline.js`；窄屏会切换成纵向时间图。
- 视觉约束：时间图的条不能压到时间刻度或"睡眠/早餐/午餐/晚餐"图例上，本地验收会用
  `getBoundingClientRect` 判定相交，任何相交都算失败；两截的标注与轴上的"相接"说明由验收
  脚本按 `data-tl-part` / `data-tl-join` 断言（不依赖中文文案）。

## 10. 工程默认值一览

| 常量 / 默认值 | 取值 | 含义与出处 |
| --- | --- | --- |
| 引擎代号 | `adaptive-v2` | 响应 `engine` 字段固定为该值 |
| 计划天数 | 按需推算，可取 1–30 | 请求参数 `days` 覆盖；样本不足时截短并提示 |
| 进度档 | `fast`（默认）/ `slow` | 请求参数 `mode`，只影响步子分配 |
| 步长曲线 | 形状函数 `φ(u) = 1 + 0.6·(1 − u)`，按总偏移与天数现场生成 | 先快后缓，末日仍保留首日约 62% 的速度；见第 2 节 |
| 每日阈值（提示） | **60 分钟/天**，前移与后移相同 | 只影响 `feasible` 与提示文案，不截断计划；见第 3 节 |
| 单日输入上限 | **120 分钟/天** | `fast` 档的可行判定与输入校验用；产品侧初始要求 |
| 早餐窗口 | 起床后 **15–30** 分钟 | 工程默认值（文献无钟点窗口） |
| 午餐起点 | 早餐与晚餐的**中点**，整体提前 **60** 分钟，夹进 [起床+120, 晚餐−240] 分钟 | 工程默认值；早先锚在“起床+180”，白天越长间隔越大（19 小时白天可达 12.5 小时），故改为取中点 |
| 午餐窗口长 | **120** 分钟 | 与早餐/晚餐窗口等长口径一致，可因连续未吃早餐前移 |
| 晚餐窗口 | 窗口长 **90** 分钟，起点为睡前 **270** 分钟（3.5 小时 + 整体提前 1 小时） | 工程默认值，锚在睡眠侧 |
| 现实窗口·午餐 | 起床 ≤ **15:00** → 午餐就近靠拢进 **11:00–15:00** | `NORMAL_WAKE_UNTIL` / `LUNCH_NORMAL_WINDOW`，社会时钟参考 |
| 现实窗口·晚餐 | 入睡不晚于次日 **06:00**（或当天 17:00 之后）→ 晚餐就近靠拢进 **17:00–22:00** | `NORMAL_SLEEP_UNTIL` / `DINNER_NORMAL_WINDOW`，越界则跳过窗口 |
| 三餐开关 | `meal_breakfast` / `meal_lunch` / `meal_dinner` | 用户级设置（`/api/settings`），默认开启 |
| 偏离静默阈值 | **≤ 30** 分钟 | 静默接受，不提示 |
| 偏离重算区间 | **30–90** 分钟 | 静默重算，每天最多一次 |
| 偏离弹窗阈值 | **> 90** 分钟 | 交由用户在 `postpone` / `recompute` / `keep` 中选择 |
| 时间图跨度 | 起床前 **120** 分钟 → 入睡后 **120** 分钟（所以随记录变化，常见 1200–1260 分钟） | 轴窗两端各留 2 小时；跨零点时整夜被拆成 `morning`/`night` 两截，见第 9 节 |
| 快照保存 | `save: true`（默认） | 生成建议即落库，偏离与达标率都以快照为基准 |
| 达标率分母 | 仅“有记录”的天 | 未记录既不算达标也不算不达标，不打断连续 |
| 写入冷却 | 10 秒/用户 | 配置项 `SSP_WRITE_COOLDOWN_SECONDS`，命中返回 429 |
| 记录保留 | 6 个月 | 定时清理任务，见 [DEPLOYMENT.md](DEPLOYMENT.md) |

**文献支撑 vs 工程默认值的边界**：只有两条有文献支撑 —— 相位移动速率（前移/后移都在 1 小时/天量级）与
“三餐只做节律锚点、不作为相位杠杆”。其余常量（起床后 15 分钟吃早餐、午餐取中点再提前 1 小时、
现实作息窗口 11:00–15:00 / 17:00–22:00、步长曲线形状、偏离分档阈值）都是工程默认值，
可按实际使用反馈调整，调整时同步更新本表与
[tests/test_advice_engine.py](../tests/test_advice_engine.py)。
